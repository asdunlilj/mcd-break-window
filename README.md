# 麦麦课间窗口 · mcd-break-window

> 在有限的课间里，告诉你**现在点什么、大概多久能取**，让学生不迟到、门店不挤爆。

基于麦当劳中国 MCP 开发。参赛作品：2026 麦当劳程序员创意开发大赛。

**首个验证门店**：`3450415` 麦当劳德阳罗江区四川工业科技学院校内商业街餐厅
（本项目需求由该店经理的真实痛点驱动）

---

## 一、解决什么问题

### 门店经理的原话（需求来源）

> 课间休息时间有限，同学们到店后再下单可能会怕等餐超时迟到；但提前把餐点好，如果等很久来取又会餐品品质不好。系统如果能提前告知大概多久可取餐，且如果能做到推荐餐品，既能减少学生焦虑，也能平缓门店高峰压力。

这个问题有两个角色、一个共同解：

| 角色 | 痛点 | 本项目的价值 |
|---|---|---|
| 学生 | 只有 10 分钟课间，不知道要等多久，怕迟到 | 下单前就给出**预计等待时长**与**课间是否来得及**的判断 |
| 学生 | 提前点好却等太久，餐品放凉影响口感 | 推荐出餐快的餐品，**缩短「做好→取走」的空窗** |
| 门店 | 课间瞬时客流集中，出餐压力陡增 | 用推荐把客流从慢餐品引导到快餐品，**平缓高峰** |

### 为什么这件事必须"算"出来

经对麦当劳 MCP 全部 **35 个 Tool** 逐项核查，**没有任何一个提供出餐时长或排队队列的实时信号**（唯一的"预计"字段 `expectDeliveryTime` 属于外送场景的预计送达时间，不适用于到店取餐）。

所以等待时长无法查询，只能**建模预估**——这正是本项目的主要技术工作。

---

## 二、核心能力

| # | 能力 | 说明 |
|:-:|---|---|
| 1 | **等待时长预估** | 输出预计分钟数 + 置信区间 + 完整系数拆解（可审计、可解释） |
| 2 | **课间窗口判定** | 在"课间时长 − 缓冲"的预算内判断"来得及 / 来不及 / 差多少" |
| 3 | **快取推荐** | 在预算内按「出餐速度 × 营养达标 × 价格区间」排序推荐 Top3 |
| 4 | **避坑提示** | 明确指出"你想点的那个会超时多久" |
| 5 | **自校准闭环** | 轮询 `query-order` 实测「下单→配餐完成」真实耗时，回填修正门店系数 |

## 三、预估模型

```
T_wait = T_base(餐品) × K_time(时段) × K_break(课间脉冲)
                        × K_campaign(促销) × K_store(门店) × K_load(负载)
```

| 系数 | 取值来源 | 说明 |
|---|---|---|
| `T_base` | 门店菜单 `query-meals` 的餐品名与分类 | 按出餐工序拆分：饮品 0.8 分、小食甜品 1.8 分、炸鸡 2.9 分、鸡肉汉堡 3.2 分、牛肉/鱼汉堡 3.5 分、安格斯 4.2 分、组合餐 3.8 分。同单多品按"最慢串行 + 其余并行折扣 0.75"叠加 |
| `K_time` | 本地校园作息表 | 早高峰 1.15、上午课 1.00、午高峰 1.55、下午课 0.95、放学高峰 1.50、夜市 1.30、宵夜 1.10 |
| `K_break` | 作息表 `break_windows` | 处于课间窗口（前后各放宽 5/15 分钟）时 ×1.35 |
| `K_campaign` | `campaign-calendar` | 当日命中"上新/联名/限时/第二份/促销"等活动时 ×1.25 |
| `K_store` | 本地校准样本 | 默认 1.0，用实测/预估比值做指数滑动（0.7 旧 + 0.3 新）修正 |
| `K_load` | 本地近 15 分钟成交样本 | 每 3 单抬升 4%，上限 1.3 |

**置信区间**：随校准样本量从 ±35% 收敛到 ±15%。

### 自校准闭环（本项目的关键设计）

```
下单 → 调用 query-order 轮询订单状态
        状态码：1 待支付 / 2 配餐中 / 3 配送中 / 4 已完成 / 5 已取消 / 10 餐厅确认配餐中
     → 命中"已配餐/已完成"时刻 → 得到真实耗时
     → calibrate() 回写 state.json → 下次预估更准
```

**全部数据来自官方 MCP，无自建采集，无爬虫。**

## 五、安装与使用

### 前置条件

- Python 3.10+（**零第三方依赖**，只用标准库）
- 麦当劳 MCP Token：https://open.mcd.cn/mcp → 登录 → 控制台 → 激活 → 复制

### 配置环境变量

```bash
# Windows (cmd)
set MCD_MCP_TOKEN=你的Token

# Windows (PowerShell)
$env:MCD_MCP_TOKEN="你的Token"

# macOS / Linux
export MCD_MCP_TOKEN=你的Token
```

> ⚠️ Token 只从环境变量读取，**不会写入任何文件或代码**。

### 使用示例

```bash
cd scripts

# 1. 连通性自检：确认服务端版本与可用 Tool
python cli.py doctor

# 2. 查看当月活动日历与今日促销状态（影响预估系数）
python cli.py campaign

# 3. 拉取门店菜单并给出全菜单预估
python cli.py menu --store 3450415

# 4. 核心功能：课间窗口快取推荐
python cli.py advise --store 3450415 --break 10 --top 3

# 5. 下单后轮询订单状态，实测真实耗时并回填校准
python cli.py watch --order <orderId> --store 3450415 --predicted 4.2
```

### 参数说明

| 参数 | 默认 | 说明 |
|---|---|---|
| `--store` | 必填 | 门店编码 `storeCode`，由 `query-nearby-stores` 获得 |
| `--break` | 10 | 课间时长（分钟） |
| `--budget` | `--break + 3` | 可接受等待上限，3 分钟为步行/取餐缓冲 |
| `--top` | 3 | 推荐条数 |

### 校园作息（真实作息表驱动）

`scripts/campus_schedule.json` 内置了**四川工业科技学院《冬季教学作息时间表》**（10 月 1 日—次年 5 月 1 日执行）。
课间窗口**不手工罗列**，而是由课程表自动推导相邻课程之间的空档，避免与作息表不一致：

```bash
python cli.py schedule          # 列出当天的所有课间窗口
python cli.py schedule --date 2026-10-17
```

输出示例（周五，自动切换到「周五、周六」作息）：

```
窗口                        起止              时长  类型
第一节课 → 第二节课           09:05–09:15      10 分钟  小课间（仅快餐品可行）
第二节课 → 第三节课           10:00–10:30      30 分钟  大课间（可选常规餐品）
第三节课 → 第四节课           11:15–11:25      10 分钟  小课间（仅快餐品可行）
第四节课 → 第五节课           12:10–13:10      60 分钟  餐段（时间充裕）
第五节课 → 第六节课           13:55–14:05      10 分钟  小课间（仅快餐品可行）
第六节课 → 第七节课           14:50–15:20      30 分钟  大课间（可选常规餐品）
第七节课 → 第八节课           16:05–16:15      10 分钟  小课间（仅快餐品可行）
第八节课 → 第九节课           17:00–19:00     120 分钟  餐段（时间充裕）
第九节课 → 第十节课           19:45–19:55      10 分钟  小课间（仅快餐品可行）
```

三类窗口对应不同的推荐策略：

| 类型 | 判定 | 脉冲系数 | 推荐策略 |
|---|---|---:|---|
| 小课间 | ≤12 分钟 | 1.35 | 只求快：推荐 4–6 分钟能出的单品 |
| 大课间 | ≥25 分钟 | 1.20 | 求吃得饱：推荐三件套等完整正餐 |
| 餐段 | ≥45 分钟 | 1.10 | 同大课间（窗口已饱和） |

`advise` **不需要手动传 `--break`**，会自动识别当前窗口与剩余时间：

```bash
python cli.py advise --store 3450415                 # 自动识别
python cli.py advise --store 3450415 --at 10:05      # 模拟时段，便于审计
```

> 换学校时只需替换 `campus_schedule.json` 里的 `periods`，窗口会自动重算。
> 门店营业时间（09:00–23:00）也在同一文件内，早于营业时间会给出提示。

## 九、设计边界与已知限制

| 限制 | 说明 | 后续方向 |
|---|---|---|
| **状态机不等于真值** | `orderStatus` 是员工手动操作的状态机。**压单时员工会批量把订单点成"已完成"清屏**，导致实测等待偏短，且偏差与负载正相关 | 已实施五道防线（R1–R5），见 [docs/data-integrity.md](./docs/data-integrity.md)；判定口径被设计为**污染无法使其变乐观** |
| 基准时长来自工序经验值，非门店实测 | MCP 不提供出餐时长，初期必然有偏差 | `watch` 命令的自校准会逐步收敛 |
| 课间窗口需手工配置 | 各校作息不同，无法从 MCP 获取 | 提供默认值 + `campus_schedule.json` 可配置 |
| 负载系数依赖本机历史样本 | 单人使用样本量有限 | 多人共享校准数据（需额外隐私设计） |
| 促销系数为粗粒度布尔判断 | `campaign-calendar` 不区分活动强度 | 按活动类型细分系数 |
| 无门店实时队列 | MCP 未开放该能力 | 若官方后续开放，可直接替换 `K_load` |
| **不解决绝对产能** | 若课间瞬时单量远超厨房产能，任何信息工具都无效 | 本工具只改变**需求结构**，不改变**需求总量** |

以上限制均为**如实披露**，不做夸大。

### 关于"门店压单把订单提前点完成"

这是本项目最严肃的一处设计挑战，处理方式已在 [docs/data-integrity.md](./docs/data-integrity.md) 中完整展开（含数字推演、五道防线、剩余风险、设计取舍的自我批评）。核心保证：

> **无论校准数据被污染成什么样，"课间是否来得及"的判定口径永远不会比未校准基线更乐观。**

代价是判定偏保守（可能低估门店效率）——这是基于"迟到 vs 多等"代价不对称所做的**故意取舍**。

可自行验证：`python tests/test_guard.py`（不依赖网络与 Token，12 项断言）。
