## 一、一句话结论

**经理最该给的不是数据，是「一次许可 + 一个人 + 两个时段」。**

两名成员独立得出的结论收敛到同一点：**唯一能给可信出餐时长与实际等待真值的路径，是允许我们在出餐口蹲店实测 2–3 个时段，并由经理指定 1 名店员在高分期做最小记录。** 其余输入都能用现有模型 + 保守假设兜底。

## 二、最少必要配合：只要 3 件事（阻塞项）

| # | 需要什么 | 为什么不可替代 | 缺失后果 |
|:-:|---|---|---|
| **1** | **允许蹲店实测 2–3 个时段**（课间、午高峰、晚高峰） | 官方无逐产品出品时间表；状态机数据被压单污染。实测是唯一能拿到"真实交付时刻"的通道 | N3 停在"经验估计"，N2 真值通道不成立 |
| **2** | **口述一份品类快慢排序**（最快 / 一般 / 最慢 三档即可） | 为蹲店实测提供抽样优先级，避免把有限产能浪费在低频品类 | 实测样本被均摊到 121 个餐品上，每项样本不足 |
| **3** | **数据使用书面授权 + 指定 1 名店员配合记录** | 涉门店真实经营数据；无人配合则只能靠学生自觉（样本量不可控） | 合规风险；真值通道时断时续 |

### ⚠️ 一个必须提前告知你的现实约束

数据侧指出：**为避免触发数据完整性防线 R3（同门店 90 秒内 ≥3 条样本判定为"批量清屏"），记录必须分散，间隔 ≥5 分钟。**

这直接把蹲店记录产能**封顶在约 12 条/小时**（不是按到单量走）。这条约束决定了整个样本量规划的规模，见第七节裁决 3。

## 四、可直接照着问的访谈提纲（12 问，按优先级）

> 口语化，用户可原样照读。前 4 问是阻塞项。本节为许可研的原始产出。

1. **课间最挤是几点到几点？跟学校大课间对得上吗？**
2. **你们现在有没有叫号？同学怎么知道自己的餐好了？**
3. **哪些餐几分钟就好、哪些要等很久？大概差多少？**（三档即可）
4. **最挤的时候后厨能同时做几份？几个人、几台设备？**
5. **同学们一般能接受等多久？超过多久会抱怨、催单，或者干脆走掉？**
6. **最忙的时候，平均一个同学从点单到拿到要等多久？店里同时有多少人在等？**
7. **能不能让我们在课间来店里实地看一两次、记一下实际出餐时间？**
8. **能不能请人在高峰期帮忙记一下每单什么时候做好？我们不会连着记，大概每 5 分钟记一单，尽量避免打扰后厨。**
9. **你们支持提前点 / 预约吗？提前多久点比较合适？**
10. **每天营业结束，能不能导一份当天的下单记录？去掉人名电话，只要时间和品类。**
11. **如果在收银台放个小屏 / 贴个二维码给同学看"大概要等多久"，可以吗？**
12. **用店里的这些数据做参赛作品，作品和宣传里能不能写店名店号、拍店内照片？需要跟学校或谁打招呼、有没有限制？**

> 第 8 问已按 R3 约束改写：明确告知"每 5 分钟记一单、避免打扰"，降低经理对配合成本的顾虑。

## 六、出餐时长获取路径裁决 ★

> 三路径评估为储海量的产出；排序采纳其推荐组合。

| 路径 | 可行性 | 样本成本 | 偏差性质 | 裁决 |
|---|---|---|---|---|
| **(a) 经理口述排序/分钟数** | 高（1 次访谈即得） | 0 | 凭印象、品类粒度粗、**系统性偏乐观（经理倾向低估自家出餐时间）** | ✅ 作**初值锚点**，不作终值 |
| **(b) 人工现场观察** | 中（需蹲店，需经理放行） | 每人次 1–2h；**受 R3 约束记录须 ≥5min 间隔，产能上限 ≈12 条/h**；累计需 ≥25 条/品类 | 记录者计时点主观（取餐口 vs 出餐口）、样本量小 | ✅ 作 `T_base` **校准主力** |
| **(c) `orderStatus` 轮询推算** | 低 | 0 边际 | **单向偏短 + 内生性**：状态机"完成"由员工手点，高峰压单越重提前量越大，误差与自变量正相关 | ⚠️ **仅作残余信号** |

**推荐组合及理由：**
1. **(a) 先给初值排序** —— 零成本、9 天内立即可得，用作冷启动与 (b) 的对照基线
2. **(b) 蹲店实测校准** —— 唯一能拿到"真实交付时刻"的通道，是精度提升的核心，务必争取
3. **(c) 轮询兜底喂 `K_store`** —— 必须强制过 R1–R5，且判定口径强制 `K_store ≥ 1.0`，只影响排序不影响"是否来得及"

### ❌ 被否决的方案

**"直接抓取门店全部历史订单，用完成时间做监督学习"** —— 否决理由：① 订单级数据评估为"拿不到"；② 即便拿到，完成时间同样被压单污染，(c) 的内生性偏差不会因样本量变大而消失，反而会更稳定地学到一个偏乐观的模型。**这是本项目最需要避免的错误方向。**

## 七、独立真值通道设计（成员产出原文）

> 本节为储海量的原始产出。核对确认：与主理人此前草稿在字段、权重、清洗规则上一致，以下为成员原文。

**字段定义（扩展 `state.json` 的 `samples[]`）**

```
channel(student_confirm / store_measured) | order_ts(下单时刻) | ready_ts(真实可取时刻)
wait_actual_min(= ready_ts − order_ts) | items[](品类组合，用于归因到 T_base)
load(采集时近 15min 样本数) | source / trust(复用现有)
```

**采集时机**
- `student_confirm`：学生在界面点"我拿到了"时打点（依赖自觉，属**弱监督**）
- `store_measured`：经理/志愿者在出餐口**按 ≥5min 间隔逐单记录**（为避免触发 R3 的 90s/≥3 条批量清屏判定，记录必须分散）

**样本量下限及推算过程**（假设：品类内标准差 σ≈1.2min，目标 95%CI 半宽 ±0.5min）

```
n = (z·σ/E)² = (1.96 × 1.2 / 0.5)² ≈ 22.1  →  取 ≥25 条/品类
门店级 K_store：spread = max(0.15, 0.35 − 0.002n)
  n=30 → 区间 ≈ ±29%；n=100 → ±15%  →  最低 ≥30 条/店，建议 100 条
若放宽到 ±0.75min，则 n ≈ 10 条/品类即可
σ 需以实测复核【待确认】
```

**清洗规则（复用 R1–R4）**

R1 物理下界（实测 < max(0.7, 基准×0.55) → 丢弃）；R2 状态跳变（仅状态机通道，首观测即完成且 <90s → 丢弃）；R3 批量清屏（同店 90s 内 ≥3 条 → 整批丢弃）；R4 负载单调性（ρ < −0.30 且 n ≥ 8 → 冻结校准）。
**R5 保守单向仅约束判定口径，不用于清洗。**

**两通道合并与加权**
- 分层存储，用 `channel` 字段区分，**不混算**（两条通道偏差性质不同）
- 权重：`student_confirm`(w=1.0，人工确认) > `store_measured`(w=0.9，含记录者误差) > 状态机轮询(w=0.4，须过 R1–R5)
- 合并式：`wait = Σ(wᵢ·actualᵢ) / Σwᵢ`；**同品类先按时段分层**再加权，避免高峰样本淹没平峰
- 冲突处理：两通道同品类均值差 > 50% → 触发人工复核，本轮不入 `K_store`

## 八、数据存储与合规边界（成员产出原文）

| 边界 | 内容 |
|---|---|
| **不能采集** | 学号 / 姓名 / 手机号 / 位置轨迹 / 支付信息 / 任何可关联到个人的订单号 |
| **不能存储** | 真实 MCP Token、学生账号凭证、原始订单明细 |
| **必须脱敏** | 订单以匿名 `session_id`(随机 UUID) 标识；时间戳可保留但须去除设备指纹 |
| **严禁行为** | **代下单把多学生订单聚合到单一账号**（合规 + 支付 + 售后风险） |

**本机 `state.json` vs 未来云端**
- 本机：单用户、本地文件、无需账号、退出即清、无跨端共享
- 云端：需 ①匿名 ID 体系 ②RLS 行级隔离 ③Token 存服务端密钥库（禁入仓）④保留期策略（原始样本 ≤90 天、聚合系数长期）
- **9 天工期下建议不引入云端**【待确认】

> 「严禁代下单聚合单一账号」这一条直接封死了最初设想的"全校下单后追踪"路径，与本项目此前独立发现的 MCP 账号边界结论一致。

## 九、主理人裁决记录（5 项，含目标下调与两处共同遗漏）

### 裁决 1：真值通道形式 —— **采纳数据侧**

产品侧并列三条候选未排序；数据侧明确推荐"蹲店实测优先"。
**裁决：以数据侧为准。** 订单导出评估为"拿不到"且不含真实出餐时刻；叫号屏拍照覆盖不全。**蹲店实测是唯一能同时产出 `T_base` 与真值的路径。**

### 裁决 2：N2 的"实时" —— **分两阶段，不是二选一**

- **阶段一（真值通道建立前）**：不做"实时"，输出保守包络估算 + 显著免责声明
- **阶段二（`student_confirm` 上线后）**：恢复实时倒计时

⚠️ 阶段二依赖一个尚未决定的前提：`student_confirm` 需要学生端有交互界面，而**学生端形态至今未定**（见裁决 4）。

### 裁决 3：样本量目标 —— **主理人核算后下调，并采纳"品类分桶"方案** ★

数据侧原始目标为"≥25 条/品类 × 8 品类 ≈ 200 条"。**主理人在核算蹲店产能后判定不可行，数据侧亦复算并确认"达不到"。**

**约束来源**：R3 要求记录间隔 ≥5 分钟 → **记录产能上限 ≈12 条/h**（这是本项目自己设的防线带来的副作用，属于设计上的内生产物）。

```
单时段有效蹲守 ≈1.5h → ≈18 条
2–3 时段         → ≈36–54 条
连续 4 天 × 3 时段 → ≈60–72 条（总量）
但这是全品类混合：高频品类 15–25 条；低频品类（安格斯、组合餐、卷类）仅 2–8 条
```

**裁决方案（采纳数据侧建议并定稿）：**

1. **品类粒度从 8 类合并为 3–4 桶**：
   - 快餐品桶 = 饮品 + 小食甜品
   - 中速桶 = 汉堡 + 卷类 + 炸鸡
   - 慢餐桶 = 安格斯 + 组合餐
2. **目标降为 ≥15 条/桶**（3–4 次蹲守内现实可达）
3. **放宽置信区间到 ±0.6–0.75min**（σ=1.2 时对应 n≈10–15/桶）
4. **跨时段、跨日合并池化**同一桶样本，不追求单时段达标
5. **优先保决策关键桶**：驱动削峰推荐的"快 vs 慢"两端，中间态可粗

**退回经验值的品类**（低到单 + 低决策影响）：安格斯厚牛堡（4.2min）、组合餐（3.8min）、卷类（2.6min，可并入炸鸡桶）；若门店量低，牛肉/鱼汉堡也可能退回。
**保住实测的桶**：饮品、小食甜品、鸡肉汉堡——到单最多，且是"快/慢"推荐排序的主角。

> **取舍声明**：这个下调让方案从"理论上完整"变成"9 天内真能做完"，代价是部分品类 `T_base` 仍是经验值。**必须在输出与文档中如实标注"经验估计"，不得伪装成实测值。**

### 裁决 4：两方都漏掉的约束 —— **学生端形态未定**

`student_confirm` 通道、N1 压力展示、N2 实时倒计时，**全部依赖"学生在哪里看到界面"**，而两方都只在待确认清单里一笔带过。
**裁决：此项必须在 Day 1 与经理沟通同时确定。** 三个候选：

| 形态 | 成本 | 优势 | 劣势 |
|---|---|---|---|
| 单文件 HTML 链接 | 零 | 今天就能用，无需账号 | 无推送、需手动打开、`localStorage` 仅本机 |
| 网页版 + 轻后端 | 中 | 多端共享、可持久化 | 需引入云端（数据侧建议 9 天内不引入） |
| 微信小程序 | 高 | 体验最好 | 个人主体在点餐类目有资质限制，审核周期不可控 |

**裁决：阶段一用「单文件 HTML 链接 + 本机 `localStorage`」，不引入后端。** 与数据侧"9 天内不上云端"的判断一致。

### 裁决 5：赏味倒计时的适用范围 —— **限制为 2 类** ★

**我此前在方案中把"官方赏味倒计时"作为一个可普遍落地的功能模板**，但数据侧的可得性评估否定了这一点：

> 各品类赏味/持有时限 —— 官方仅发布薯条 7min、汉堡 20–30min，其余品类**拿不到**。

**裁决：赏味倒计时只对薯条类与汉堡类展示，其余品类不展示倒计时**（展示"未知"比展示编造阈值更诚实）。若经理能补充其他品类的持有时间，再逐类开放。
