# 下单后实时等待追踪 —— 需求可行性与逻辑审查

> 审查时间：2026-10-16  
> 审查对象：三项新需求（实时压力展示 / 提前点完成时的等待推算 / 引用官方出品时间标准）  
> 结论：**两项可以做，一项在现有能力下做不到；另有两处逻辑漏洞会导致输出不可信。**

我把你的话拆成三条独立需求：

|    #   | 需求                                                        | 我的理解                                            |

## 三、逻辑漏洞（逐条，直接指出）

### 漏洞 1：**"前方等待人数"没有任何数据来源，只能编造**

我对麦当劳 MCP 全部 35 个 Tool 的字段做了检索：

| 关键词                              |       命中数 |
| -------------------------------- | --------: |
| `排队` / `queue`                   |     0 / 0 |
| `前方` / `等待人数`                    |     0 / 0 |
| `门店负载` / `忙碌` / `busy`           | 0 / 0 / 0 |
| `orderCount` / `待制作` / `pending` | 0 / 0 / 0 |

`query-order` 只能查**你自己那一单**；`order-list` 只能查**你自己**的历史订单。  
**不存在任何返回门店整体队列深度的接口。**

→ 如果界面上写"前方还有 8 单"，这个 8 是我编的。**给客户展示编造的数字，比不展示更糟**——一旦他验证一次不符，整个工具的可信度就归零。  
→ 可替代：**压力指数**（由时段系数、当日活动、本店历史样本合成），并明示"基于历史规律估算，非门店实时排队"。

### 漏洞 2：**"完成时间 − 下单时间"无法在数学上还原真实等待**

你的方案是：拿"完成时间 − 下单时间"，再"结合当前压力程度"修正。

问题在于：**你已经假设了完成时间是被提前点的**。既然它被污染，那 `完成时间 − 下单时间` 就**不是测量值，而是真实等待的下界**。要用"压力"去修正它，必须先知道"提前量与压力的函数关系"——而这个关系本身就是未知量。

**同一份数据里同时估计两个未知量（真实等待 + 提前量函数），是不可识别的（not identifiable）。** 这跟"只用一把不准的尺子，测不出尺子本身偏了多少"是同一类问题。

→ 必须引入**独立于该状态机的真值通道**，二选一：

- **(a) 学生侧确认**：学生点一下"我拿到了"，记录真实时刻 —— 本项目已有 `source="user"` 通道，但依赖学生自觉
- **(b) 门店侧提供**：经理给出实测出餐时长，作为外部锚点

**没有 (a) 或 (b)，N2 做不出来。**

### 漏洞 3：**学生拿不到 orderId，且订单归属是单一账号**

`query-order` 需要 `orderId`，且只能查询**当前 MCP Token 所属账号**的订单。这意味着：

- 学生用自己的麦当劳账号下单 → 系统**既拿不到 orderId，也查不到状态**
- 只有"通过本工具下单"的订单能追踪 → 而这意味着**所有学生的订单都挂在同一个账号下**
- 一个账号不可能承接几百名学生的并发订单，也不应该这么做（支付、发票、售后全部纠缠在一起）

→ **"给全校学生做下单后追踪"这个产品形态，在 MCP 能力边界内不成立。**  
→ 现实可行的只有两种收窄形态：

- **单人/小范围形态**：一人一账号，追踪自己的订单（适合你自己、或少数几个同学）
- **班级/社团代下单形态**：一人统一代买 N 份，追踪这一笔订单（适合团餐场景）

### 漏洞 4：**静态单文件 HTML 无法实现"实时"**

当前交付物是**无后端、无账号、可离线的单文件 HTML**。"实时显示 + 持续保存"需要三样东西：常驻轮询、状态持久化、多端共享。

- 单文件 + `localStorage` 可以做到：**本机持久化 + 打开时刷新一次**（能覆盖"刷新不丢"，但做不到"后台持续更新"）
- 要真正实时 → 必须有服务端（云数据库 + 定时任务 + 小程序/网页前端）

→ 需要你明确：**是否接受引入后端**。这决定了 N1/N2 能做到什么程度。

### 漏洞 5：**展示"现在很忙"可能反噬门店的成交**

学生看到"当前高峰，预计等 12 分钟"，一部分人会**转向别处或直接放弃下单**。  
这对"削峰"是好事，对**成交额**是坏事。

→ 这是门店要自己拍板的取舍，不是我们能替他决定的。建议**把压力分为三档且不显示具体数字**（顺畅 / 偏忙 / 高峰），弱化劝退效果。

### 漏洞 6：**N3 的前提只部分成立**（详见第四节）

官方**有**时间标准，但**没有**"逐产品出品时长表"。你说的"按官方标准确定各产品的出品时间"，官方只给到**品类级**（汉堡、薯条）和**端到端级**（点餐到取餐）。

→ 正确的做法不是"照抄官方出品类表"，而是：**用官方数据做锚点校准，用门店实测补齐单品差异**。

这正是你原始痛点里"**提前点好，等很久来取餐品品质不好**"的**官方量化依据**。

这条比"预计还需等待多久"更能击中原痛点，而且**100% 有官方依据**。建议把它作为这一轮的优先项。

## 八、补充核查（2026-10-17）：能不能"调取门店正在制作的订单列表"？

这条建议值得单独回答，因为它是最容易想到、也最容易做错的一条路。

### 8.1 结论：取数层不存在，加密层无从谈起

> **原始建议：实时调取门店每个时刻的正在制作订单列表，然后加密，只给客户展示数字。**

拆成两步看：

| 步骤 | 是否可行 | 原因 |
|---|---|---|
| ① 取数：拿到门店所有在制订单 | **不可行** | 35 个 Tool 中没有任何一个返回门店级订单列表 |
| ② 展示：加密后只给数字 | 技术上可行 | 但 ① 拿不到数据，这一步没有输入 |

现有订单类接口的真实覆盖范围：

| 接口 | 能查什么 | 查不到什么 |
|---|---|---|
| `query-order(orderId)` | **单笔**订单详情（需 orderId） | 别人的订单、门店列表 |
| `order-list` | **本账号**历史订单（实测 4 笔） | 别人下的单、门店队列 |
| `mall-order-list` | 本账号**商城**订单 | 门店在制订单 |

`query-order` 的返回里确实含 `customerNickname`、`mobilePhone` 等字段——
**但这只对"你自己账号的订单"成立**。要读别人的订单，首先得拿到别人的 `orderId`，
而没有任何接口能枚举它们。

### 8.2 更进一步：即使能拿到，也不该拿

这一点比技术限制更重要：

- 他人订单包含**姓名、手机号**（`query-order` 实测返回 `customerNickname` / `mobilePhone`）
- "加密后只展示数字"保护的是**传输与展示**环节，**不改变"未经授权获取他人个人信息"这一行为的性质**
- 参赛合规明确不采集个人信息（见 `docs/manager-input-checklist.md` 第八节）
- 一旦为了"体感"去抓别人订单，整个项目的合规基调就崩了——而这个项目最值钱的部分恰恰是**可信**

**所以这条路不是"难"，是"不该走"。**

### 8.3 但"体感"这个目标是合理的，有两条合规替代

#### 替代 A：取餐码（已实现，真实数据）

实测：`query-order` 的返回**包含 `pickupCode`**。查 2026-09-03 那笔订单得到：

```json
"pickupCode": "35062"
```

这是**门店给出的真实序号**，不是估算值。已接入追踪页展示：

```
追踪依据：物理下界 2.5 分钟 · 取餐码 35062 · 订单状态 已完成（存疑）
```

数字本身就有体感，而且**零隐私风险**——它只属于下这一单的人自己。

#### 替代 B：利特尔法则（Little's Law）

排队论的基本关系：

```
L = λ × W
  L = 队列长度（前方还有几份）
  λ = 到达率（门店每分钟接多少单）
  W = 平均停留时间（每单从下单到取餐要多久，模型已能算）
```

- `W` 已有（六系数模型输出）
- `λ` 可用**取餐码差**标定：同一门店两次下单，`ΔpickupCode / Δt ≈ λ`
  - 例：两次下单间隔 30 分钟、取餐码从 35062 走到 35098 → `λ ≈ 36 / 30 = 1.2 单/分钟`
- 也可由门店直接给出"高峰单量/10 分钟"（已在配合清单里列为待确认项）

**这样算出的"前方约 N 份"是有数学依据的估算，不是编的。** 前提是 `λ` 有标定来源；
没有 `λ` 时只能给时间（分钟数），不能给份数。

### 8.4 当前状态与下一步

| 项 | 状态 |
|---|---|
| 取餐码展示 | ✅ 已接入追踪页 |
| 真实订单状态追踪 | ✅ 已实现（需 Token + 真实 orderId） |
| 按时间给"还需等待" | ✅ 已实现（保守包络口径） |
| 按份数给"前方还有几份" | ⏳ **待 λ 标定**（需 ≥2 笔同店订单，或门店给单量） |
| 门店在制订单列表 | ❌ 不做（无接口，且不该做） |

**下一步可做**：把每笔订单的 `pickupCode` + 时间戳持久化，累计 ≥2 笔后自动算出该店 `λ`，
再在页面给出"前方约 N 份"的估算值，并标注"基于本店出餐速率推算"。

### 8.5 顺带修正的一个真实 bug

本次实测发现订单状态码的映射写错了。官方 schema 是：

```
1 待支付 / 2 配餐中 / 4 配送中 / 6 已完成 / 7 已取消 / 8 已评价 / 10 餐厅确认配餐中
```

此前误写成 `4 已完成 / 5 已取消 / 6 已评价`。已修正，并补上实测发现的另一种口径：
`orderStatus` 返回中文、`status` 返回数字（已完成时 `status = "40"`）。
