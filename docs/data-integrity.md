# 数据完整性：批量点完成问题与五道防线

> 本文档回答一个由门店经理提出的现实质疑：**门店在压单时会把订单提前点成"完成"清屏，这会污染本项目的校准数据。怎么解决？**
> 全文给结论、给数字、给代码位置，便于逐条审计。

---

## 一、结论先行

| 问题 | 结论 |
|---|---|
| 质疑是否成立 | **完全成立**。这不是普通噪声，而是**与自变量相关的系统性偏差**（内生性污染） |
| 能否解决 | **能控制到可接受范围**，但不可能根除。方案是五道纵深防线 + 一个架构性保护 |
| 是否影响工具核心价值 | **不影响**。判定口径被设计成"污染无法使其变乐观"（R5） |
| 是否影响门店问题本身 | 压单行为会被**检测并转化为风险提示**，而不是被掩盖 |

---

## 二、污染机制：为什么这不是"普通误差"

### 2.1 数据流与污染点

```
用户下单
   │
   ├─► 真实事件：餐品真正做好并被取走      ← 我们想要的真值（MCP 无法观测）
   │
   └─► 状态机事件：orderStatus 变为 4「已完成」 ← 员工手动点击（MCP 可观测）
              ▲
              └── 污染发生在这里：压单时员工批量点完成以清空操作屏，
                  此事件可早于真实交付数分钟，且提前量与压单严重程度正相关
```

### 2.2 为什么它比"随机噪声"危险得多

普通测量噪声会互相抵消；而这个偏差有三个恶化性质：

**性质 1：方向单一（只会偏短）**
员工不会"提前"把没做好的餐标成完成吗？会。反向偏差（把做好的餐压着不标记）没有动机。所以误差几乎单向——**实测等待恒小于真实等待**。

**性质 2：与自变量正相关（内生性）**
高峰压单越严重 → 提前点完成的幅度越大。而"高峰"恰恰是模型要预测的对象之一（`K_time` / `K_load`）。
测量误差与自变量相关时，任何基于该数据的拟合都会**系统性低估高峰系数**。

**性质 3：在最需要准确的时段伤害最大**
后果不是"平均差一点"，而是"越忙越乐观"——把学生推向迟到的正是这个方向。

### 2.3 用数字算一遍后果

假设某校内门店真实情况与状态机记录如下：

| 时段 | 真实等待 | 状态机记录 | 提前量 | 误差方向 |
|---|---:|---:|---:|---|
| 平峰 | 3.0 分钟 | 2.9 分钟 | 0.1 | 可忽略 |
| 午高峰 | 9.0 分钟 | 5.0 分钟 | 4.0 | **严重低估** |
| 课间脉冲 | 7.5 分钟 | 4.5 分钟 | 3.0 | **严重低估** |

若直接用这组数据校准 `K_store`：

```
target = mean(actual / predicted)
       = mean(2.9/3.0, 5.0/9.0, 4.5/7.5)
       = mean(0.967, 0.556, 0.600)
       ≈ 0.71
```

`K_store` 会被拉到 **0.71**。此后高峰预估：

```
真实需要 9 分钟，模型给出 9 × 0.71 ≈ 6.4 分钟
```

→ 模型会告诉学生"6 分钟就好"，学生在 10 分钟课间里实际要等 9 分钟，**迟到风险被放大**。

**这就是为什么必须处理，而不能"先把校准做上，以后再说"。**

## 三、为什么不能"干脆不做校准"

因为那样就退化成一张静态查表：所有门店、所有时期用同一套基准值，
无法反映任何门店差异，也无法反映门店自身随时间的变化（人员、动线、设备）。

**校准是必要的增强层，问题在于它必须"只可信时启用"。**

这也是本项目架构上的核心决定：

> **校准是增强层，不是基础层。**
> 即使校准被完全关闭或冻结，`advise` 仍能给出完整的预估与推荐——
> 只是失去门店个性化修正。

## 四、五道防线

代码位置：`scripts/calibration_guard.py`（阈值全部为具名常量，便于审计与调参）

### R1 物理下界 —— 拦截"物理不可能"的样本

| 项 | 值 |
|---|---|
| 规则 | 实测时间 < `max(0.7 分钟, 基准出餐 × 0.55)` → 丢弃 |
| 代码 | `physical_floor()` / `audit_sample()` |
| 为什么有效 | 现制汉堡需要煎制+组装，任何厨房都不可能低于此下界。低于下界的 `已完成` **逻辑上必然不是真实交付**，无需统计推断即可判定 |
| 示例 | 基准 3.2 分钟的汉堡，实测 0.5 分钟 → 下界 1.76 分钟 → **丢弃** |

这是唯一**非统计学**的硬过滤，置信度最高。

### R2 状态跳变 —— 拦截"首次观测即完成且间隔过短"

| 项 | 值 |
|---|---|
| 规则 | 与状态机口径下，首次观测即 `已完成` 且距下单 < 90 秒 → 丢弃 |
| 代码 | `audit_sample()` 中 `first_observed_seconds` 检查 |
| 为什么有效 | 正常流程必然是 `待支付 → 配餐中 → 已完成`。首次观测就直接已完成，说明轮询窗口之前就已被人为推进 |
| 边界 | 用户确认口径（`source="user"`）**不受此限**——真值优先于启发式规则 |

### R3 批量清屏 —— 拦截"短窗口内样本聚集"

| 项 | 值 |
|---|---|
| 规则 | 同门店 90 秒内出现 ≥ 3 条校准样本 → 判定为操作屏批量点击，**该批全部丢弃** |
| 代码 | `detect_batch_clear()` |
| 为什么有效 | 真实交付是逐单发生的：厨房不可能在 90 秒内真实完成并交付 3 单以上热食。聚集即为人手批量操作的特征 |
| 防误杀 | 已用分散样本（10s / 300s / 900s）验证不触发 |

### R4 负载单调性 —— 拦截"整段时期的数据被压短"

| 项 | 值 |
|---|---|
| 规则 | 对同门店最近样本做 Spearman 秩相关；若「实测等待」与「负载」显著负相关（ρ < −0.30 且样本 ≥ 8）→ **冻结自动校准** |
| 代码 | `check_load_monotonicity()`（秩相关为自实现，无第三方依赖） |
| 为什么有效 | **理论上负载越高真实等待必然越长**。若实测呈现显著负相关，说明实测值被外部因素系统性压短——这是内生性污染的直接指纹 |
| 冻结后行为 | 停止更新 `K_store`，回退到未校准基线，并在输出中明确告警 |
| 解除方式 | `python cli.py unfreeze --reason "..."`（需人工复核） |

R4 是唯一针对"**整批数据不可信**"而非"单条样本不可信"的防线。

### R5 保守单向 —— 架构性保护（最关键）

前三道防线处理"训练数据是否可信"，但**只要数据还能进模型，就仍有残余风险**。
R5 直接消除后果：

| 项 | 值 |
|---|---|
| 规则 | 维护两个口径：<br>**点估计**（`safe=False`）：允许 `K_store < 1.0`，仅用于**排序**<br>**保守包络**（`safe=True`）：强制 `K_store ≥ 1.0`，用于**「课间是否来得及」的判定** |
| 代码 | `PrepModel.estimate(..., safe=True)` + `recommend()` |
| 为什么有效 | 无论校准数据被污染成什么样，**判定口径永远不会比未校准基线更乐观** |
| 代价 | 判定偏保守，可能低估门店效率 → 这是**故意付出的代价** |

**代价不对称是 R5 的设计依据：**

| 判断偏差 | 后果 | 严重度 |
|---|---|---|
| 高估等待 | 学生多等一会儿 / 放弃购买 / 改选别的店 | 低 |
| 低估等待 | **学生迟到**——本项目要解决的核心痛点被击穿 | 高 |

既然两侧代价不对称，就应把不确定性**全部推向代价低的那一侧**。

示例（来自 `tests/test_guard.py` 实测输出）：

```
门店系数原始值  : 0.6
点估计口径 K_store: 0.6 → 2.34 分钟（用于排序）
判定口径 K_store: 1.0 → 3.90 分钟（用于判定）
```

即使系数被压低到 0.6，判定口径仍按 1.0 计算。

### R5 补充：硬钳制

`clamp_store_factor()` 把 `K_store` 限制在 **[0.85, 2.50]**，防止单批异常样本把系数推到荒谬区间。

## 五、把污染信号变成功能

压单行为除了污染数据，本身也是**对学生有价值的信息**：

> 如果本系统观测到订单被异常快速地标记为完成（触发 R1/R2），
> 说明门店正处于压单状态——**该订单很可能尚未真正做好**。

因此工具的输出会附带提示：

```
⚠️ 检测到订单异常快速完成（可能为门店压单清屏），
   建议到店后向柜台确认实物，不要以状态为准。
```

**原来的数据缺陷，变成了对学生的风险预警。** 这是本方案里唯一"化害为利"的部分。

## 六、诚实的边界：拦不住什么

| 剩余风险 | 说明 | 现状 |
|---|---|---|
| 中度污染（不触发任何阈值） | 提前 1–1.5 分钟、且分散发生 → R1/R2/R3 都不触发 | **R5 兜底**：只影响排序，不影响判定 |
| 长期缓慢的乐观漂移 | 每次都在阈值内，但方向一致 | R4 的负相关检验会在积累到 8 条样本时发现 |
| 用户确认口径被误用 | 若用户随手填一个数 | 无解。但代价由用户自己承担（他自己被误导） |
| 无法观测真实交付 | MCP 不提供该信号，本项目亦无法观测 | **本方案的根本性限制**，已在 README「已知限制」中披露 |

**不存在"完全解决"的方案**——因为真值本身在 MCP 的能力边界之外。
本方案的目标是把影响压缩到"不会导致错误决策"，而不是"测量精确"。

## 七、这个工具能不能缓解经理的问题

必须把问题切成两块回答，否则容易夸大。

### ✅ 能解决的：决策不确定性（学生侧）

| 之前 | 之后 |
|---|---|
| 完全不知道要等多久 | 得到预估区间 + 完整系数拆解 |
| 只能凭感觉赌一把 | 得到「课间是否来得及」的明确判定（保守口径） |
| 提前点好却等太久，餐品变凉 | 推荐出餐快的餐品，缩短「做好→取走」空窗 |

### ✅ 能缓解的：高峰压力（门店侧）

推荐排序会把需求**从慢工序餐品引导到快工序餐品**：

| 餐品 | 基准出餐 | 引导方向 |
|---|---:|---|
| 安格斯厚牛堡 | 4.2 分钟 | ↓ 减少课间点单 |
| 牛肉/鱼汉堡 | 3.5 分钟 | ↓ |
| 卷类 | 2.6 分钟 | ↑ 优先推荐 |
| 小食甜品 | 1.8 分钟 | ↑ |
| 饮品 | 0.8 分钟 | ↑ |

在同样的总单量下，**改变需求结构就能降低厨房的瞬时峰值负荷**——这是削峰。

### ❌ 不能解决的：绝对产能

如果课间 10 分钟里门店一次涌入 200 单，而厨房 10 分钟最多做 80 单，
那么**任何信息工具都救不了**——那是产能问题，不是信息问题。

本工具只能**改变需求的结构与时间分布**，不能**改变需求的总量**，更不能扩容厨房。
这一点必须说清楚，否则就是夸大。

### ❌ 不能消除压单行为本身

压单是员工在超载下的应急操作。工具通过削峰可以**降低压单发生的概率与强度**，
但不能消除。不过工具能**检测到它**，并把它转化为对学生的风险提示。

### 📊 一句话总结

> 本工具把「学生赌运气 + 门店被动挨打」变成
> 「学生知道该点什么、门店的峰值被削平一点」。
> **它优化的是信息与需求结构，不是产能。**

## 八、如何自行审计

```bash
cd mcd-break-window
python tests/test_guard.py
```

该脚本**不依赖网络、不依赖 MCP Token**，用构造数据逐条验证 R1–R5，
并在末尾跑一个端到端场景（真实等待 8.4 分钟、状态机给出 3 分钟），
观察污染样本是否被拦截、判定口径是否仍然保守。

已实测输出（12 项断言全部通过）：

```
污染样本 #1 actual=3.0 → accepted=False | R2 状态跳变：首次观测即已完成且间隔 40s < 90s
污染样本 #2 actual=2.8 → accepted=False | R2 状态跳变：...
污染样本 #3 actual=3.2 → accepted=False | R2 状态跳变：...
用户确认真值 actual=8.4 → accepted=True
更新后门店系数 = 1.12
完整性报告：采纳 1 条，丢弃 3 条，冻结 False
```

查看任意时刻的完整性状态：

```bash
python cli.py integrity     # 采纳/丢弃条数、来源分布、冻结原因、最近被拒样本明细
python cli.py unfreeze      # 人工复核后解除冻结
```

## 九、设计取舍的自我批评

| 取舍 | 代价 | 为什么仍然这么选 |
|---|---|---|
| 判定用保守包络 | 可能低估效率，误判"来不及"而流失订单 | 迟到 vs 多等，代价不对称 |
| R3 用 90 秒 / 3 条阈值 | 真实连续下单（如帮同学带多单）可能被误杀 | 误杀的代价是少一条训练样本（可忽略） |
| R4 冻结而非修正 | 污染期完全失去校准能力 | 无可靠方法从被污染数据中还原真值，宁可不用 |
| 未引入机器学习模型 | 精度上限低于数据驱动方法 | 零真实标注数据下，学习模型无法工作；且可解释性对门店经理更重要 |

**最需要改进的一点**：目前缺少一个**独立于 MCP 的真值通道**。
如果未来能引入"用户按键确认已取餐"的闭环（本方案已提供 `source="user"` 通道，
但依赖用户自觉），污染问题才能真正从"控制"走向"解决"。
