# 预估模型的推导与边界说明

## 1. 问题定义

给定「门店 + 餐品清单 + 当前时间 + 课间时长」，输出：

- 预计等待分钟数 `T_wait` 及其置信区间
- 该餐品在当前课间窗口内是否来得及
- 若来不及，需提前（或延后）多少分钟

## 2. 为什么必须建模，而不能查询

对麦当劳 MCP 全部 35 个 Tool 的 schema 做关键词全量检索，结果：

| 关键词 | 命中数 | 说明 |
|---|---:|---|
| `备餐` | 0 | — |
| `出餐` | 0 | — |
| `ready` | 0 | — |
| `estimate` | 0 | — |
| `wait` | 0 | — |
| `queue` | 0 | — |
| `预计` | 2 | 均为 `expectDeliveryTime`：**外送**场景的预计送达时间，不适用于到店取餐 |

**结论：服务端不提供到店取餐的等待时长信号。** 因此 `T_wait` 必须由本项目建模。

## 3. 模型形式

采用**乘性系数模型**，而非学习模型，理由有三：

1. **可解释**：门店经理能看懂每个系数的含义，愿意采纳与调参
2. **冷启动可用**：无需历史数据即可给出合理初值（学习模型在零样本时无法工作）
3. **可校准**：每个系数都对某一类可观测信号负责，能独立修正

```
T_wait = T_base × K_time × K_break × K_campaign × K_store × K_load
```

## 4. 各系数的推导

### 4.1 `T_base` —— 餐品基准出餐时长

按门店菜单（`query-meals`）返回的餐品名与分类，映射到出餐工序：

| 类别 | 基准（分钟） | 依据 |
|---|---:|---|
| 饮品 | 0.8 | 多为分装/直出，工序最短 |
| 小食甜品 | 1.8 | 薯条/派/冰淇淋需短时加工 |
| 卷类 | 2.6 | 需现制但结构简单 |
| 炸鸡 | 2.9 | 炸制需固定时长，且常需等待批次 |
| 鸡肉汉堡 | 3.2 | 需现煎肉饼 + 组装 |
| 牛肉/鱼汉堡 | 3.5 | 牛肉饼煎制时间更长 |
| 安格斯厚牛堡 | 4.2 | 厚饼 + 双层芝士，工序最长 |
| 组合餐 | 3.8 | 含汉堡类主件 + 配餐 |

**同单多品的叠加规则**：制作是部分并行的。

```
T_base(多品) = max(单品时长) + Σ(其余单品时长) × 0.75
```

即最慢的一样串行打底，其余按 0.75 的并行折扣叠加。

### 4.2 `K_time` —— 时段系数

基于校园门店客流曲线：

| 时段 | 系数 | 场景 |
|---|---:|---|
| 07:30–09:00 | 1.15 | 早高峰（早餐赶课） |
| 09:00–11:30 | 1.00 | 上午课时段（基准） |
| 11:30–13:10 | 1.55 | 午高峰（全天峰值） |
| 13:10–14:15 | 1.20 | 午后 |
| 14:15–16:40 | 0.95 | 下午课时段 |
| 16:40–18:30 | 1.50 | 放学高峰 |
| 18:30–21:45 | 1.30 | 夜市时段 |
| 21:45–23:00 | 1.10 | 宵夜时段 |
| 其余 | 0.60 | 非营业时段 |

### 4.3 `K_break` —— 课间脉冲

课间是**微高峰**：大量学生在同一窗口涌入。命中配置的 `break_windows`
（前后各放宽 5 / 15 分钟）时叠加 **1.35**。

> 该系数是"门店削峰"价值的直接体现——正是因为课间存在脉冲，把客流
> 从慢餐品引导到快餐品的收益才显著。

### 4.4 `K_campaign` —— 促销系数

`campaign-calendar` 返回当月活动日历。当日命中"上新 / 联名 / 限时 / 第二份 /
促销"等关键词时叠加 **1.25**。

局限：该接口不区分活动强度，因此只能做粗粒度布尔判断。

### 4.5 `K_store` —— 门店系数（自校准）

默认 1.0。通过 `query-order` 轮询实测「下单 → 配餐完成」的真实耗时后修正：

```
target  = mean(actual / predicted)   # 取该店最近 30 个样本
new     = old × 0.7 + target × 0.3   # 指数滑动，抑制异常样本
```

### 4.6 `K_load` —— 负载系数

统计本机记录中该门店**近 15 分钟**的成交样本数 `n`：

```
K_load = min(1.0 + 0.04 × floor(n / 3), 1.3)
```

即每 3 单抬升 4%，上限 1.3。

## 5. 置信区间

```
spread = max(0.15, 0.35 − 0.002 × samples)
区间 = T_wait × (1 ± spread)
```

样本从 0 增长到 100 条时，区间从 ±35% 收敛到 ±15%。

## 6. 推荐打分

在课间预算 `budget = 课间时长 + 缓冲(默认 3 分钟)` 内，按四维加权打分：

```
score = w_speed × 速度分 + w_complete × 完整度 + w_nut × 营养分 + w_price × 价格分
```

### 6.1 权重随窗口松紧自适应

```
tight = clamp((30 − budget) / 18, 0, 1)        # 1 = 紧窗口，0 = 宽窗口

w_speed    = 0.15 + 0.35 × tight               # 0.15 ～ 0.50
w_complete = 0.05 + 0.30 × (1 − tight)         # 0.05 ～ 0.35
w_nut      = 0.20 + 0.10 × (1 − tight)         # 0.20 ～ 0.30
w_price    = 1 − 上述三项                       # 0.20 ～ 0.25
```

| 窗口 | tight | 速度 | 完整度 | 营养 | 价格 | 实际行为 |
|---|---:|---:|---:|---:|---:|---|
| 小课间 7 分钟 | 1.00 | 0.50 | 0.05 | 0.20 | 0.25 | 求快：推荐 4–6 分钟能出的单品 |
| 大课间 25 分钟 | 0.11 | 0.19 | 0.32 | 0.29 | 0.21 | 求饱：推荐三件套等完整正餐 |
| 餐段 90 分钟 | 0.00 | 0.15 | 0.35 | 0.30 | 0.20 | 同上（窗宽已饱和） |

**为什么要引入「完整度」**：早期版本把速度权重写死为 0.55，结果 28 分钟的大课间
仍然只推荐最快的那三个单品——因为同一批餐品在速度、价格、营养上同时占优，
**排序对权重完全不敏感**。加入与窗口正相关的完整度维度后，宽窗口才会推荐吃得饱的正餐。

### 6.2 各维度计算

| 维度 | 计算 |
|---|---|
| 速度分 | `max(0, 1 − T_wait / (2 × budget))` |
| 完整度 | 按类别查表：组合餐 1.00 / 安格斯 0.70 / 汉堡 0.60 / 卷与炸鸡 0.50 / 小食甜品 0.30 / 饮品 0.10 |
| 营养分 | 350–650 kcal 得 1.00；250–350 得 0.85；650–900 得 0.70；>900 得 0.45；过低得 0.60；**无数据取中性 0.60**；钠 >1000mg 减 0.15；蛋白 ≥20g 加 0.05 |
| 价格分 | ≤30 元 1.00；≤45 元 0.85；≤60 元 0.65；更高 0.45；无价格 0.50 |

**超预算的强惩罚**：`score × 0.35`，确保"来不及"的餐品不会排在前面。

### 6.3 选择阶段的两条规则

1. **正餐优先**：第一轮只从完整度 ≥ 0.30 的餐品中挑选，正餐不足 `top_k` 时才用
   饮品/小食补齐。避免出现「课间推荐前三名里两杯可乐」这种荒谬结果。
2. **同类别最多 2 项**：既保证口味多样，也让需求更均匀地分摊到不同工序
   （对门店削峰有利）。

### 6.4 已知的排序缺陷与修复记录

| 缺陷 | 症状 | 修复 |
|---|---|---|
| 速度权重写死 | 大课间仍只推最快单品，排序对权重不敏感 | 引入完整度维度 + 松紧自适应权重 |
| 营养分悬崖 | 不在营养表里的餐品直接掉到 0.3，等于用**数据可得性**冒充**营养质量** | 无数据取中性 0.60，改为连续打分 |
| 分类顺序错误 | 「龙焰鸡腿堡三件套」先命中「鸡腿堡」规则，被当成单品汉堡，基准时长与类别都错 | 组合餐规则提到最前 |
| 价格分阶梯过陡 | 15–35 元以外一律 0.6，套餐被不成比例压低 | 改为四档温和惩罚 |

## 7. 已知限制（如实披露）

| 限制 | 影响 | 缓解 |
|---|---|---|
| `T_base` 来自工序经验值 | 初期预估存在系统偏差 | `watch` 自校准会逐步收敛 |
| 课间窗口需手工配置 | 各校作息不同 | 提供默认值 + JSON 可配置 |
| `K_load` 依赖单机样本 | 单用户样本量有限 | 多人共享需额外隐私设计，暂未实现 |
| `K_campaign` 粒度粗 | 不区分活动强度 | 后续可按活动类型细分 |
| 无门店实时队列 | 突发大单无法预知 | 若官方开放该能力可直接替换 `K_load` |

## 8. 可验证性

模型全部系数均对外暴露（`Breakdown` 结构），可通过 `cli.py advise` 的
「模型明细」段落逐项审计。任何一次输出的计算链路都可完整复现。
